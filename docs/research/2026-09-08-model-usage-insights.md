# Исследование: расход Codex по моделям

## Вывод

Модельную детализацию стоит строить только по локальным агрегатам токенов. `account/usage/read` в Codex App Server даёт активность аккаунта и дневные корзины, но не подтверждённую долю лимита, израсходованную конкретной моделью. Поэтому интерфейс показывает токены, их долю в определяемой части локальной истории, оценочную стоимость и ведущий проект — но не «Sol съел 40% ChatGPT Pro».

## Практика открытых реализаций

- [codex-usage-dashboard](https://github.com/YUHAO-corn/codex-usage-dashboard) разделяет локальные токены по моделям, включая input/output/cache, и строит дневную динамику.
- [codex_usage](https://github.com/capisoft-lib/codex_usage) связывает локальные metadata с моделью, проектом и сессией, не смешивая их с облачной квотой.
- [Codex App Server](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md) описывает чтение usage/rate limits как отдельный API-контур; модельная атрибуция в нём не заявлена.

## Выбранные правила

1. Деноминатор для доли модели — только сумма токенов с известной моделью.
2. Если модель определена не для всей локальной истории, интерфейс сообщает покрытие вместо выдумывания полной разбивки.
3. «Главный проект» — проект с наибольшим числом локально учтённых токенов этой модели; это не анализ содержания задачи.
4. Цена остаётся «оценкой» и показывается только при наличии локальной расчётной величины.
